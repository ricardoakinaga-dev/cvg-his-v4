## 3. Fluxo Ponta a Ponta — Provado por Analise de Codigo

O fluxo `billing.record.created` funciona da seguinte forma (confirmado via leitura de codigo):

```
1. Cliente chama POST /encounters
   → server.ts:1426

2. Encounter criado internamente
   → BillingService.createRecord() chamada (ensureRecord)
   → packages/modules/billing/src/index.ts:107
   → this.#onRecordCreated?.(record) executado

3. Callback em runtime.ts:173
   → webhooks.dispatch(accountId, 'billing.record.created', {...})

4. WebhooksService.dispatch():
   → Busca webhooks ativos para o evento (repository.findActiveByEvent)
   → Para cada webhook: cria WebhookDeliverySummary com status='pending'
   → repository.createDelivery(delivery) → PERSISTIDO NO BANCO
   → void #deliverWithRetry(webhook, delivery, payload) → HTTP POST async

5. Retry: 3 tentativas com backoff 5s/30s/90s
   → Atualiza status do delivery para 'delivered' ou 'failed'

6. Cliente consulta: GET /webhooks/{id}/deliveries
   → server.ts:3556
   → webhooks.listDeliveries(webhookId)
   → repository.findDeliveriesByWebhook(webhookId) → LIDO DO BANCO
```

O mesmo vale para `billing.status_changed` (PATCH /billing/{id}/status → BillingService.updateStatus → onStatusChanged callback).

```bash
  -H "Content-Type: application/json" \
  -d '{"username":"...","password":"..."}'

# c) Registrar webhook
curl -X POST http://localhost:3000/webhooks \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \

# d) Criar encounter (dispara billing.record.created)
curl -X POST http://localhost:3000/encounters \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"patientId":"...","ownerId":"...","type":"ambulatory"}'

# e) Consultar deliveries
curl http://localhost:3000/webhooks/{webhookId}/deliveries \
  -H "Authorization: Bearer TOKEN"

# f) Verificar status: delivered ou failed (dependendo se endpoint responde 2xx)
```
