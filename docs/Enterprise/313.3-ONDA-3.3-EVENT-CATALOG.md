# ONDA 3.3 — Event Catalog e Expansão de Webhooks

## 1. Decisão: Onda 3.3

### Escolha: Event Catalog + Expansão de Webhooks

**Justificativa:**

| Critério                         | Avaliação                                                                                    |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| **Valor de negócio**             | Alto — mais eventos habilitam mais integrações downstream sem código novo                    |
| **Risco de implementação**       | Baixo — usa infraestrutura webhook já existente (WebhooksService, DatabaseWebhookRepository) |
| **Dependências externas**        | Nenhuma — não requer vendor, approval ou credenciamento                                      |
| **Reaproveitamento do backbone** | Alto — 100% do código de Onda 3.2 é reutilizado                                              |
| **Escalabilidade futura**        | Alta — event catalog formaliza o padrão para eventos futuros                                 |
| **Tempo de execução**            | Curto — apenas wiring de callbacks e documentação                                            |

### Alternativas descartadas

| Alternativa               | Motivo do descarte                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| PIX / Pagamento           | Alto risco — depende de gateway, credenciamento, reconciliação financeira. Postergar para Onda 3.4+ |
| WhatsApp Business API     | Risco médio-alto — processo de aprovação do WhatsApp pode levar semanas. Postergar para Onda 3.4    |
| Motor Fiscal (NF-e/NFS-e) | Alto risco — complexidade fiscal, dependência de certificações. Postergar para Onda 3.5             |

### Decisão de Nomenclatura — Eventos de Scheduling

**Nome implementado:** `appointment.scheduled`

**Justificativa:**

- O callback no serviço é `onAppointmentCreated` (nome do hook interno), mas o evento é `appointment.scheduled` para refletir o status inicial do agendamento no momento da criação
- `appointment.scheduled` é semanticamente mais preciso para o domínio de scheduling: o evento representa a reserva de um horário, não apenas o registro do objeto
- Consistente com o payload que inclui `status: 'scheduled'` no momento do dispatch
- O evento `appointment.status_changed` cobre transições subsequentes (check-in, cancelamento, conclusão)
- `appointment.status_changed` é consistente com `billing.status_changed` e `encounter.status_changed`
- Decisão validada por Executores 23 e 24

**Nota:** O evento `appointment.scheduled` é disparado em `SchedulingService.createAppointment()` via callback `onAppointmentCreated`. Eventos de mudança de status subsequentes (check-in, cancelamento, conclusão) disparam `appointment.status_changed`.

### Pattern de Implementação

Cada novo evento segue o mesmo padrão usado em `BillingService`:

```typescript
// 1. Adicionar callback opcional na interface de opções do serviço
export interface XxxServiceOptions {
  readonly repository?: XxxRepository;
  readonly onEventoCreated?: (data: EventData) => Promise<void>;
  // ... outros callbacks
}

// 2. Armazenar callback no construtor
public constructor(options?: XxxServiceOptions) {
  this.#onEventoCreated = options?.onEventoCreated;
}

// 3. Disparar no ponto relevante do domínio
await this.#onEventoCreated?.(payload);

// 4. No runtime.ts, conectar ao WebhooksService
const xxx = new XxxService({
  repository: repos.xxx,
  onEventoCreated: async (data) => {
    await webhooks.dispatch(data.accountId, 'xxx.evento_created', data);
  }
});
```
