## 5. Próxima Frente — Análise para Decisão (Onda 3.4)

### 5.1 Opções Considered

| Opção                                  | Risco      | Dependência                             | Valor de Negócio    | Tempo Estimado |
| -------------------------------------- | ---------- | --------------------------------------- | ------------------- | -------------- |
| **PIX / Pagamentos**                   | Alto       | Gateway, credenciamento, reconciliation | Alto (receita)      | 8-12 semanas   |
| **WhatsApp Business API**              | Médio-Alto | Aprovação WhatsApp (semanas), templates | Alto (engajamento)  | 6-8 semanas    |
| **Motor Fiscal (NF-e/NFS-e)**          | Alto       | Certificações, compliance               | Médio               | 12+ semanas    |
| **Webhook UI (gestão de assinaturas)** | Baixo      | Nenhuma                                 | Médio (operacional) | 2-3 semanas    |

### 5.2 Recomendação: **Webhook Management UI**

**Justificativa:**

1. **Risco mínimo** — não requer vendor, approval ou credenciamento
2. **Valor operacional** — habilita gestores a registrarem webhooks sem depender de API direta
3. **Reaproveita backbone** — usa infraestrutura existente (WebhooksService, rotas, repository)
4. **Tempo curto** — 2-3 semanas para MVP funcional
5. **Não bloqueia** — pode ser paralelo a decisão de PIX/WhatsApp

**Alternativa recomendada em segundo lugar:** WhatsApp Business API (apesar do risco de aprovação, o valor de engajamento é alto para clínicas veterinárias).

### 5.3 O que NÃO recomendo para Onda 3.4

- **PIX**: muito cedo — falta infraestrutura de reconciliation financeira e risk management
- **Motor Fiscal**: alto risco sem clareza de certificação necessária no Brasil para software de gestão Veterinária

## 6. Decisão de Nomenclatura Registrada

Os nomes dos eventos de scheduling foram definidos e validados:

- **`appointment.scheduled`** — disparado quando `SchedulingService.createAppointment()` cria agendamento com status inicial `scheduled` (via callback `onAppointmentCreated`)
- **`appointment.status_changed`** — disparado em mudanças de status subsequentes (`checkIn` → `checked_in`, `cancelAppointment` → `cancelled`)

Decisão validada por Executores 23 e 24. Justificativa: alinhamento com nomenclatura de status e consistência com `billing.status_changed` e `encounter.status_changed`.
