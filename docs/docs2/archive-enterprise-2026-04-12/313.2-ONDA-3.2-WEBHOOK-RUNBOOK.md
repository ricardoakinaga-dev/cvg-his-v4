## 3. Registro de Webhook

```
POST /webhooks
Authorization: Bearer <token>
Content-Type: application/json

{
  "url": "https://seu-sistema.com/webhook",
  "events": ["billing.record.created", "billing.status_changed"],
  "secret": "sua-chave-secreta-opcional"
}
```

Resposta `201`:

```json
{
  "id": "wh_...",
  "accountId": "acc_...",
  "url": "https://seu-sistema.com/webhook",
  "events": ["billing.record.created", "billing.status_changed"],
  "isActive": true,
  "createdAt": "2026-04-08T...",
  "updatedAt": "2026-04-08T..."
}
```

## 6. Atualizar Webhook

```
PATCH /webhooks/{webhookId}
Authorization: Bearer <token>
Content-Type: application/json

{
  "url": "https://novo-endpoint.com/webhook",
  "events": ["billing.record.created"],
  "isActive": false
}
```

## 7. Deletar Webhook (soft-delete)

```
DELETE /webhooks/{webhookId}
Authorization: Bearer <token>
```

Retorna `204`. O webhook é desativado (`isActive = false`), não removido. Deliveries existentes são cascade-deleted.

## 8. Payload Entregue ao Receiver

```json
{
  "id": "whpay_...",
  "event": "billing.record.created",
  "timestamp": "2026-04-08T...",
  "accountId": "acc_cvg_demo",
  "data": {
    "id": "bil_...",
    "accountId": "acc_cvg_demo",
    "encounterId": "enc_...",
    "patientId": "pat_...",
    "ownerId": "own_...",
    "status": "pending",
    "createdAt": "2026-04-08T..."
  }
}
```

Headers HTTP:

| Header                  | Valor                                         |
| ----------------------- | --------------------------------------------- |
| `Content-Type`          | `application/json`                            |
| `X-Webhook-ID`          | ID do webhook                                 |
| `X-Webhook-Event`       | Nome do evento (ex: `billing.record.created`) |
| `X-Webhook-Delivery-ID` | ID da delivery                                |

## 9. Interpretação de Retry e Failure

O retry é configurado com 3 tentativas e backoff exponencial:

| Tentativa | Delay após falha | Status após falha         |
| --------- | ---------------- | ------------------------- |
| 1         | 5s               | `pending` + `nextRetryAt` |
| 2         | 30s              | `pending` + `nextRetryAt` |
| 3         | 90s              | `failed` (final)          |

- **Sucesso**: `status = "delivered"`, `responseStatus = 2xx`
- **Falha após 3 tentativas**: `status = "failed"`, `responseStatus = 4xx/5xx/null`
- **Timeout**: 10s por tentativa
- **Não há DLQ separado**: deliveries com `status = "failed"` permanecem no banco para auditoria

## 10. Status de Delivery — Significado

| Status      | Significado                                        |
| ----------- | -------------------------------------------------- |
| `pending`   | Delivery criado, ainda não tentou ou está em retry |
| `delivered` | Receiver respondeu com 2xx na primeira tentativa   |
| `failed`    | Todas as tentativas exauridas (3x) sem sucesso     |

## 11. Cascade Delete

Quando um webhook é deletado (`DELETE /webhooks/{id}`), todas as deliveries associadas são removidas via `ON DELETE CASCADE`.

## 13. Validação Manual

```bash

  -H "Content-Type: application/json" \
  -d '{"username":"...","password":"..."}'

# 2. Registrar webhook (substituir TOKEN)
curl -X POST http://localhost:3000/webhooks \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url":"https://webhook.site/SEU-ID","events":["billing.record.created"]}'

# 3. Listar webhooks
curl http://localhost:3000/webhooks \
  -H "Authorization: Bearer TOKEN"

# 4. Criar billing record (dispara billing.record.created)
# via fluxo normal de encounter

# 5. Inspecionar deliveries
curl http://localhost:3000/webhooks/{webhookId}/deliveries \
  -H "Authorization: Bearer TOKEN"
```

## 14. Limitações Conhecidas

- **Sem HMAC**: receiver não pode verificar assinatura criptográfica — apenas `secret` opcional é armazenado
- **Sem UI**: gestão via API REST apenas
- **Sem worker separado**: retry é feito no mesmo processo (fire-and-forget com `void`)
- **Onda 3.2 vs 3.3**: Onda 3.2 entregou 2 eventos originais; Onda 3.3 expandiu para 8 eventos no total
- **Delivery log não é exposto**: apenas o owner do webhook pode ver suas deliveries

## 16. Como Adicionar Novo Evento (Guia Operacional)

### Passo 1: Definir o payload do evento

Criar interface em `packages/shared/contracts/` (exemplo):

```typescript
// packages/shared/contracts/src/events/encounter.events.ts
export interface EncounterCreatedPayload {
  id: string;
  accountId: string;
  patientId: string;
  ownerId: string;
  type: 'ambulatory' | 'emergency' | 'inpatient';
  status: string;
  createdAt: string;
  createdByUserId: string;
}
```

### Passo 2: Adicionar callback no serviço

Em `packages/modules/{module}/src/index.ts`, adicionar callback na interface de opções:

```typescript
interface {Service}Options {
  // ...existing options
  readonly onEvent?: (data: EventPayload) => Promise<void>;
}
```

No construtor:

```typescript
public constructor(options?: {Service}Options) {
  // ...existing initialization
  this.#onEvent = options?.onEvent;
}
```

No método que dispara o evento:

```typescript
public async createEncounter(...) {
  const encounter = { /* ... */ };
  await this.#onEvent?.(encounter);
  return encounter;
}
```

### Passo 3: Conectar no runtime.ts

```typescript
const encounters = new EncountersService({
  // ...existing deps
  async onEncounterCreated(encounter) {
    await webhooks.dispatch(encounter.accountId, 'encounter.created', encounter);
  }
});
```

### Passo 4: Documentar no event catalog

Adicionar entrada no `docs/Enterprise/313.4-ONDA-3.3-EVENT-CATALOG-PREPARATION.md`.

### Passo 5: Atualizar OpenAPI (se necessário)

Se o payload do evento requer novos campos no schema, adicionar em `apps/api/src/openapi.yaml`.
