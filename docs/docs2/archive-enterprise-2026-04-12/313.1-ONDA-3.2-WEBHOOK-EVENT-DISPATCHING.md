| Opção                    | Valor                                           | Risco                                                    | Complexidade                           | Decisão                 |

| **Webhook MVP**          | Alto — infraestrutura base para todas as outras | Baixo — já existe módulo em `packages/modules/webhooks/` | Baixa — 70% do código já existe        | ✅ **ESCOLHIDA**        |

### Por que Webhook MVP?

1. **Infraestrutura reutilizável** — webhooks são o backbone para PIX, WhatsApp, email, e qualquer outra integração futura
2. **Código existente** — módulo `webhooks/` completo com repository, retry, e rotas de gestão
3. **Baixo risco** — não depende de provedor externo, credenciais, ou aprovações
4. **Recorte mínimo viável** — apenas fazer um módulo disparar eventos quando operações acontecem
5. **Alinhado com o plano** — webhooks mínimos operacionais é entregável explícito dos 90 dias

## 4. Recorte Mínimo — Onda 3.2

### Objetivo

Fazer **um módulo** disparar **um evento** via webhook quando uma operação acontecer, provando que o backbone funciona.

### Evento piloto: `billing.record.created`

**Por que billing?**

- Domínio de alto valor para integração com pagamentos
- Billing record é criado no encounter (fluxo clínico → financeiro)
- Simples de trigger — qualquer criação de encounter dispara

### Arquitetura proposta

```
┌─────────────────┐    dispatch(event)    ┌──────────────────────┐
│ BillingService  │ ──────────────────────→│  WebhookEventBus     │
│ (onRecordCreated)│                      │  (singleton)          │
└─────────────────┘                       └──────────┬───────────┘
                                                     │
                                         ┌───────────▼───────────┐
                                         │ WebhooksService        │
                                         │ (dispatch → HTTP POST) │
                                         └────────────────────────┘
```

### Implementação

1. Criar `packages/shared/events/src/webhook-event-bus.ts` com interface `WebhookEventBus`
2. Adicionar `onRecordCreated?: (record: BillingRecordSummary) => void` em `BillingServiceOptions`
3. No runtime, conectar: `billingService.onRecordCreated = (record) => webhooks.dispatch(record.accountId, 'billing.record.created', record)`
4. Documentar o padrão de evento no event catalog

### Eventos futuros (catalogo inicial)

| Evento                   | Trigger               | Domínio       |
| ------------------------ | --------------------- | ------------- |
| `billing.record.created` | Billing record criado | Billing       |

Os testes WH-001 a WH-003 cobrem:

- WH-001: registro, recuperação, listagem, update, soft-delete
- WH-002: dispatch cria delivery log; webhooks inativos não disparam
- WH-003: cascade delete de deliveries ao deletar webhook

### Fluxo ponta a ponta — Confirmado por análise de código

```
1. POST /webhooks           → WebhooksService.register()  → DB (webhooks table)
2. BillingService.ensureRecord() → onRecordCreated() → webhooks.dispatch('billing.record.created', ...)
3. WebhooksService.dispatch()   → findActiveByEvent() → HTTP POST para URL registrada
4. Delivery log → webhook_deliveries (status: pending → delivered/failed)
5. Retry: 3 tentativas com backoff 5s / 30s / 90s
6. GET /webhooks/{id}/deliveries → lista deliveries do DB
```

## 9. Riscos e Mitigações

| Risco                                  | Prob  | Impacto | Mitigação                                         |

| Módulos acoplados ao EventBus          | Baixa | Baixa   | Interface simples, injeção via callback           |
