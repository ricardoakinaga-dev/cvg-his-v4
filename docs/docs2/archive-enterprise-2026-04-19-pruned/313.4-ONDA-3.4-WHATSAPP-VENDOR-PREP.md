# ONDA 3.4 — Integração Vendor-Assisted: WhatsApp Business API

## 1. Decisão: Onda 3.4

### Escolha: WhatsApp Business API — Lembrete de Consulta

**Caso de uso MVP:** Envio automático de lembrete de consulta via WhatsApp quando `appointment.scheduled` é disparado.

**Justificativa:**

| Critério               | Avaliação                                                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Valor de negócio**   | Alto — lembretes reduzem no-show, impacto direto em receita                                                      |
| **Escopo mínimo**      | 1 webhook consumidor + 1 NotificationService provider                                                            |
| **Reaproveitamento**   | Alto — usa `appointment.scheduled` (existente), `NotificationsService` (existente), webhook dispatch (existente) |
| **Risco de aprovação** | Médio-alto — Meta/WhatsApp requer WABA verificado (2-4 semanas)                                                  |
| **Risco técnico**      | Baixo — provedor (Twilio ou 360dialog) já está no contrato (`packages/contracts/src/notifications.ts:156-158`)   |
| **Tempo de execução**  | Médio — depende de aprovação externa                                                                             |

### Alternativas descartadas

| Alternativa       | Motivo do descarte                                                                    |
| ----------------- | ------------------------------------------------------------------------------------- |
| PIX / Pagamento   | Alto risco — gateway, credenciamento, reconciliação, compliance financeiro. Postergar |
| SMS direto        | Menor valor que WhatsApp (taxa de abertura menor, custo por mensagem similar)         |
| E-mail            | Baixo impacto em lembrete de consulta — baixa taxa de leitura imediata                |
| Push notification | Depende de app instalado — não aplicável no contexto tutors                           |

## 3. Arquitetura Proposta — MVP Mínimo

```
appointment.scheduled (runtime.ts)
    │
    └── webhooks.dispatch('appointment.scheduled', payload)
            │
            └── [Consumer] AppointmentReminderWorkflow (Exec 28)
                    │
                    ├── OwnerLookup (OwnersService)
                    ├── PatientLookup (PatientsService)
                    ├── NotificationSettingsLookup (NotificationSettings)
                    │
                    └── WhatsAppProviderService
                            ├── TwilioWhatsAppAdapter (ou NoOp se desabilitado)
                            └── Envia via Twilio REST API
                                    │
                                    └── notification.sent → webhooks (via NotificationsService)
```

### Fluxo implementado (Exec 28-29)

1. **Trigger**: `SchedulingService.createAppointment()` → callback `onAppointmentCreated` → `webhooks.dispatch('appointment.scheduled', ...)` AND `appointmentReminderWorkflow.onAppointmentScheduled(appointment)` (fire-and-forget)

2. **Consumer**: `AppointmentReminderWorkflow.onAppointmentScheduled(appointment)`:
   - Busca telefone do tutor via `RuntimeOwnerLookup.getOwnerPhone(ownerId)` → usa contacts do OwnersService real (prefere whatsapp, senão phone)
   - Se não houver telefone → retorna `{ processed: true, sent: false, error: "No WhatsApp contact" }`
   - Busca nome do tutor via `RuntimeOwnerLookup.getOwnerName()`
   - Busca nome do paciente via `RuntimePatientLookup.getPatientName()` → usa PatientsService.getOrThrow()
   - Busca nome da clínica via `RuntimeSettingsLookup` (default: "Clínica Veterinária")
   - Monta `AppointmentReminderData` com visitType traduzido
   - Invoca `WhatsAppProviderService.sendAppointmentReminder(data)`

3. **Resultado**: `{ sent: boolean, messageId?: string, error?: string }`
   - Provider pode ser `TwilioWhatsAppAdapter` (com credenciais reais), `NoOpWhatsAppAdapter` (desabilitado), ou lançar `ProviderNotConfiguredError`

4. **Resultado**: `{ sent: boolean, messageId?: string, error?: string }`

### Ambientes e configurações

| Variável de ambiente   | Descrição                               | Exemplo          |
| ---------------------- | --------------------------------------- | ---------------- |
| `WHATSAPP_ENABLED`     | Ativa ou desativa o canal               | `true` / `false` |
| `WHATSAPP_PROVIDER`    | `twilio` ou `360dialog`                 | `twilio`         |
| `WHATSAPP_API_KEY`     | API Key do provider (Twilio SID/secret) | `ACxxxxxxxx`     |
| `WHATSAPP_FROM_NUMBER` | Número verificado (somente números)     | `551155555555`   |

> **Importante**: Nenhuma credencial real deve ser commitada no repositório. Usar `.env` ou secrets manager.

### Origem das configurações

O `EnvNotificationSettingsProvider` (Exec 30) lê variáveis de ambiente em tempo de inicialização do runtime:

- Se `WHATSAPP_ENABLED !== 'true'` → retorna `null` → provider desabilitado (fail-safe)
- Se `WHATSAPP_API_KEY` vazio → retorna `null`
- Se `WHATSAPP_FROM_NUMBER` vazio → retorna `null`
- Provider padrão: `twilio`

### Matriz de Comportamento por Configuração

| WHATSAPP_ENABLED       | WHATSAPP_API_KEY       | WHATSAPP_FROM_NUMBER | Resultado                                                                  |
| ---------------------- | ---------------------- | -------------------- | -------------------------------------------------------------------------- |
| `false` / não definido | qualquer               | qualquer             | `{ sent: false, error: "Provider not configured" }` — fail-safe, sem crash |
| `true`                 | vazio                  | qualquer             | `{ sent: false, error: "WHATSAPP_API_KEY is required" }`                   |
| `true`                 | `ACxxx`                | vazio                | `{ sent: false, error: "WHATSAPP_FROM_NUMBER is required" }`               |
| `true`                 | `ACxxx`                | `55...`              | Chama Twilio API (retorna AUTH_FAILURE em sandbox)                         |
| `true`                 | credencial real válida | número verificado    | Envio real via Twilio (produção)                                           |

**Flow interno**:

```
appointment.scheduled
    → AppointmentReminderWorkflow.onAppointmentScheduled()
        → getOwnerPhone() → null? → { sent: false, error: "No WhatsApp contact" }
        → getWhatsAppConfig() → null? → { sent: false, error: "Provider not configured" }
        → WhatsAppProviderService.sendAppointmentReminder()
            → validateConfiguration() → invalid → { sent: false, error }
            → sendMessage() → fetch Twilio → error → { sent: false, error }
            → success → { sent: true, messageId: "..." }
```

**Falha segura**: qualquer etapa que falhe retorna `{ processed: true, sent: false, error: "..." }` — o appointment creation nunca falha por causa do WhatsApp.

### Limitações atuais

- Não há banco de dados de NotificationSettings — usa env vars apenas
- Provider 360dialog ainda é stub (NoOp)
- Não há persistência do resultado de envio em `NotificationRepository`
- Não há scheduler/worker — o fluxo é on-demand via callback

## 6. Inbound Webhook — Confirmação do Tutor

### Endpoint implementado (Exec 32)

**Rota**: `POST /webhooks/whatsapp/inbound` (sem autenticação — webhook vendor)

**Payload**: Twilio-style inbound callback

```json
{
  "MessageSid": "SM...",
  "From": "whatsapp:+5511999998888",
  "To": "whatsapp:+551155555555",
  "Body": "CONFIRMAR",
  "AppointmentId": "appt_123"
}
```

**Respostas** (plain text):

| Mensagem do tutor                | Resposta             |
| -------------------------------- | -------------------- |
| `CONFIRMAR` / `CONFIRM`          | `CONFIRMADO`         |
| `CANCELAR` / `CANCELAR CONSULTA` | `CANCELADO`          |
| `REMARCAR`                       | `AGUARDANDO REMARCA` |
| qualquer outra                   | `OK`                 |

**Comportamento**:

- Cada inbound é registrado no audit log com `whatsapp.inbound_received`
- Não há autenticação HMAC nesta versão (hauler for future improvement)
- Sem impacto no appointment status — apenas logging nesta versão
- Fail-safe: qualquer payload malformed é aceito e retorna `OK`
